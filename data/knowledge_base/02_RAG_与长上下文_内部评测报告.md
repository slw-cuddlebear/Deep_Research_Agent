# RAG 与长上下文方案：内部评测报告

> ⚠️ 本文档是 **Deep Research Agent 项目的演示语料**。文中评测数据为**构造的示例数据**，
> 用于演示"本地知识库能提供网上检索不到的内部信息"，不代表任何真实产品实测结果。

## 1. 评测设置

- 语料：3 类超长文档，分别为 120 页技术手册、300 页合规文档、45 页合同
- 问题集：每类 20 题，共 60 题，均需要跨段落整合
- 对比方案：
  - **A. RAG**：固定 600 字切片 + BGE 向量检索 + Top-5 送入 32K 上下文模型
  - **B. 长上下文**：全文塞入 200K 上下文模型，不做检索
  - **C. 分层**：先用 RAG 粗排定位章节，再把命中的章节整段送入长上下文模型

## 2. 评测结果

| 指标 | A. RAG | B. 长上下文 | C. 分层 |
|---|---|---|---|
| 答案正确率（人工判定） | 71.7% | 88.3% | **90.0%** |
| 引用可溯源率 | **100%** | 62% | 96.7% |
| 单次问答成本（相对值） | **1.0** | 14.6 | 4.2 |
| P95 延迟 | **2.4s** | 26.8s | 8.9s |
| 可处理文档上限 | 无上限 | 约 200 页 | 无上限 |
| 新增文档的边际成本 | 仅索引增量 | 每次全量重读 | 索引增量 + 部分重读 |

## 3. 关键发现

1. **长上下文在答案质量上确实占优，但代价是 14.6 倍成本与 11 倍延迟**。
   在 300 页合规文档上，长上下文方案 P95 延迟达到 **51 秒**，已经超出交互式场景的容忍上限。
2. **长上下文最大的问题是无法溯源**。引用可溯源率只有 **62%**——
   模型经常给出正确结论但指错段落位置，这在合规、法务场景是不可接受的。
3. **分层的性价比最高**：用 RAG 做粗排（定位到章节级）再让长上下文精读，
   正确率追平纯长上下文（90.0% vs 88.3%），成本只有其 **28.8%**（4.2 / 14.6）。
4. **文档规模是分水岭**：文档总量在 **50 页以内**时，长上下文方案的综合体验更好（省掉索引维护）；
   超过 **200 页**后长上下文的延迟与成本迅速失控，必须走检索路线。

## 4. 我们的选型倾向

采用**分层策略**，并把阈值定在 50 页：

- 单文档 < 50 页且问题不需要跨文档 → 直接长上下文，省掉索引
- 单文档 ≥ 50 页 或 需要跨文档整合 → RAG 粗排 + 章节级精读
- 合规/法务类场景 → **强制走 RAG 路线**，因为引用可溯源是硬要求

## 5. 一个容易忽略的细节

检索质量决定了分层方案的上限。在评测中，把固定 600 字切片换成
**按语义主题的动态切片**后，A 方案的正确率从 71.7% 提升到 **78.3%**，
而 C 方案从 90.0% 提升到 **93.3%**。
也就是说：**切片粒度是分层方案的隐藏瓶颈**，粗排阶段漏掉的章节，后面的长上下文再强也救不回来。
