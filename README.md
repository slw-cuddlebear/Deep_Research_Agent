# 🔎 Deep Research Agent

模拟人类研究员工作方式的深度研究 Agent：输入一个复杂研究问题，自动完成**任务规划 → 多源检索 → 信息提取 → 反思补充 → 生成带引用的结构化研究报告**。

传统 RAG 回答的是"文档里有什么"，无法处理需要多源检索、多步推理、信息整合的研究型问题。本项目用 LangGraph 把研究流程建成一张状态图，由 Agent 自行判断"该查什么、查够了没有、还差什么"，并对报告的每一处结论标注可追溯的来源。

> 对标产品：OpenAI Deep Research、Perplexity、Genspark

## ✨ 功能特性

- 🧩 **问题拆解**：把复杂问题拆成 3~5 个有逻辑递进的子问题，并给出建议检索词
- ✏️ **计划可人工调整**：CLI 交互模式与 Web 端表格均可直接修改子问题与检索词
- 🌐 **多源检索**：网页搜索（Tavily 优先，DuckDuckGo 兜底）+ 本地知识库语义检索
- ⚡ **并发执行**：检索、正文抓取、事实提炼均为线程池并发
- 📄 **信息提取**：Trafilatura 抓正文（BeautifulSoup 兜底）→ LLM 提炼结构化事实（含原文摘录与置信度）
- 🧹 **事实治理**：相似度去重 + 数值冲突检测 + 来源可信度打分
- 🔁 **反思循环**：判断信息充分性，不充分则自动生成补充检索词再搜，四道规则刹车保证收敛
- 🔗 **引用溯源**：按来源编号、越界编号剔除、连续重编号，网络与本地来源分组展示
- 📝 **报告生成**：摘要 / 正文 / 结论 / 参考文献 / 研究过程附录，导出 Markdown、HTML、PDF
- 📚 **本地知识库**：Chroma + BGE 语义检索，增量索引，与网页结果统一尺度融合
- 🖥️ **过程可视化**：Streamlit 实时展示思考、检索、反思轨迹，支持在线预览与三种格式下载
- ⏱️ **可观测性**：本地 span 树追踪（耗时 / Token / 成本），可选上报 LangFuse
- 💰 **成本核算**：按官方价目表计算，区分高峰/错峰与缓存命中
- 🧪 **量化评估**：策略消融实验 + 自研 LLM 裁判评估报告质量
- 🩺 **环境体检**：`--doctor` 一次查清依赖、Key、网络、字体、知识库、可观测性
- 🔌 **离线演示**：无 API Key 也能完整跑通界面与链路（假模型 + 假搜索）
- 🐳 **容器化**：Dockerfile + docker-compose，已实测构建并运行通过

## 🏗️ 系统架构

```
用户输入研究问题
       ↓
┌─────────────────────────────┐
│      任务规划器 (Planner)      │  拆解为子问题 → 生成研究计划
└─────────────────────────────┘
       ↓
┌─────────────────────────────┐
│      搜索执行器 (Searcher)     │  网页搜索 + 本地知识库检索 → 融合排序
└─────────────────────────────┘
       ↓
┌─────────────────────────────┐
│      信息提取器 (Extractor)    │  抓正文 → 提炼事实 → 去重 → 冲突检测
└─────────────────────────────┘
       ↓
┌─────────────────────────────┐
│      反思决策器 (Reflector)    │  信息是否充分？──否──┐
└─────────────────────────────┘                      │
       │ 是                                          │
       ↓                                             │
┌─────────────────────────────┐                      │
│      报告生成器 (Writer)       │  大纲→逐章写作→引用  │
└─────────────────────────────┘                      │
       ↓                                             │
  输出研究报告 + 引用来源        ←─────── 补充搜索 ─────┘
```

状态由 **LangGraph** 管理：节点是处理步骤，条件边决定"继续搜索"还是"进入写作"。会跨轮累积的状态字段（搜索结果 / 网页 / 事实 / 事件）挂 `operator.add` reducer，并行分支写回时自动合并。

## 🚀 快速开始

### 1. 克隆仓库

```bash
git clone https://github.com/slw-cuddlebear/Deep_Research_Agent.git
cd Deep_Research_Agent
```

### 2. 创建虚拟环境

```bash
python -m venv .venv

# Windows
.venv\Scripts\activate

# macOS / Linux
source .venv/bin/activate
```

### 3. 安装依赖

```bash
pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
```

### 4. 配置环境变量

```bash
cp .env.example .env
```

编辑 `.env`：

```env
# 必填：DeepSeek API Key（https://platform.deepseek.com）
DEEPSEEK_API_KEY=sk-你的key

# 必填：Tavily Key（https://tavily.com），免费额度 1000 次/月
TAVILY_API_KEY=tvly-你的key

# 可选：模型下载加速
HF_ENDPOINT=https://hf-mirror.com
```

> **关于免费兜底搜索**：代码保留了 DuckDuckGo 作为免 Key 兜底引擎，但部分网络环境不可达
> （实测 `html.duckduckgo.com:443` 与 `search.brave.com:443` 均超时）。
> 因此建议配置 Tavily Key；缺 Key 时程序会给出明确提示，而非静默失败。

### 5. 环境体检（建议先跑一次）

```bash
python main.py --doctor
```

一次性检查：Python 版本、依赖完整性、Key 是否填写、各服务网络连通性、中文字体、
本地知识库索引、可观测性配置，并真实调用 DeepSeek / Tavily 验证 Key 有效性。
缺失项会直接列成待办清单。

### 6. 运行

```bash
# 图形界面
streamlit run app.py

# 命令行跑一次研究
python main.py "2024 年以来国产大模型的推理成本下降了大约多少，主要靠哪些技术手段实现？"

# 先查看研究计划，可手动修改后再执行
python main.py "研究问题" --interactive

# 无 API Key 验证链路是否通畅（假模型 + 假搜索，不消耗额度）
python main.py "研究问题" --offline

# 单元自检（不需要 Key）
python tests/test_phase1.py

# 探测当前网络下哪些搜索引擎可用
python tests/probe_search_engines.py

# 端到端批量测试并汇总指标
python run_tests.py
```

## 🧠 核心机制

### 反思循环的收敛保障

反思决策器让 LLM 判断"信息够不够"，但**是否真的再搜一轮由规则层决定**，共四道刹车：

| # | 刹车 | 触发条件 |
|---|---|---|
| 1 | 最大搜索轮数 | 达到 `MAX_ITERATIONS`（默认 3）强制进入写作 |
| 2 | 补充词为空 / 全部重复 | LLM 表示要继续但未给出全新检索词 |
| 3 | 上一轮零新增事实 | 再搜也只会得到重复内容，及时止损 |
| 4 | 每轮补充词上限 | 最多接受 3 条，且新词之间互查重复 |

即使 LLM 每轮都坚持"信息不足"，链路也必定在有限步内收敛。

### 引用溯源

引用编号**按来源分配而非按事实分配**——同一网页提炼出的多条事实共用一个引用号，
参考文献中不会重复出现同一链接。流程：

```
事实按来源分组 → 按可信度排序编号 [1..N] → 编号随 Prompt 下发给 LLM 要求照抄
  → 写作完成 → 剔除越界编号 → 按首次出现顺序重排为连续 1..K
  → 只保留正文真正引用过的来源，输出参考文献
```

关键设计：

- **让模型照抄编号而不是自行编号**：写作 Prompt 直接给出 `[1] 事实陈述` 与可用编号白名单，
  比让模型自由发挥再事后对齐可靠得多
- **写完再校验**：模型偶尔会写出不存在的引用号，这类越界编号会被剔除并计入 `越界引用数` 指标
- **重编号消除断号**：不重编号会出现 `[1][3][7]` 这类断号（部分来源未被引用），
  重编号后编号连续，同时天然剔除"提取了却没用上"的来源
- **来源可信度打分**：按域名给出 0~1 的可信度（政府/学术/权威媒体 0.9，行业媒体 0.6，
  聚合与 UGC 0.4），高可信来源优先获得靠前的引用号

### 本地知识库与混合检索

除网页搜索外，Agent 还会检索 `data/knowledge_base/` 下的本地文档，两路结果融合后共同进入阅读与提炼。

```bash
python main.py --rebuild-kb          # 放入文档后强制重建索引（首次检索也会自动构建）
python main.py "研究问题" --no-local  # 只用网页搜索
```

索引是**增量**的：以文件指纹（文件名 + 大小 + 内容哈希）判断语料是否变化，
未变化则直接复用，不会每次启动都重新向量化。

**融合排序（不使用额外精排模型）**：

1. **统一尺度归一化**——网页侧给 0~1 相关性分，本地侧给余弦相似度，
   两路使用同一个 min/max 归一化，以保留跨来源的相对强弱
2. **本地轻微加权**（`LOCAL_SCORE_BOOST=1.15`）——内部资料通常比泛泛的网页更贴身
3. **保底名额 + 按分数竞争**（`LOCAL_MIN_SLOTS=2`）——本地片段数量天然少于网页，
   纯按分数排序容易被整体挤掉，故保底 2 条，其余名额由两路自由竞争
4. **相关度闸门**（`LOCAL_MIN_SCORE=0.45`）——低于该分数视为"本地库没有这块知识"。
   基于 BGE 余弦相似度实测标定：相关子问题最高分 0.59~0.77（均值 0.67），
   无关问题 0.33~0.42（均值 0.40）；取 0.45 时相关查询 8/8 全部召回、无关查询仅 1/8 误召

**来源标识与引用**：本地片段以 `local://<文件名>#chunk-<n>` 标识，与网页 URL 共用同一套编号逻辑；
但报告不会暴露 `local://` 协议——参考文献分为「网络来源」与「本地知识库文档」两组，编号跨组保持连续。

> `data/knowledge_base/` 自带 3 篇**演示语料**用于开箱验证混合检索，文中数据为构造示例，
> 已在文档开头明确标注，请勿当作真实测量结果。

### 报告导出

| 格式 | 说明 |
|---|---|
| Markdown | 主产物，可直接导入 Typora / 飞书 / Notion |
| HTML | 带样式的单文件网页 |
| PDF | xhtml2pdf 渲染，中文字体运行时自动探测，中文按版面宽度主动断行 |

**中文字体**：探测覆盖 Windows（等线/黑体/微软雅黑）、macOS（苹方/宋体）、Linux（文泉驿/Noto CJK）。
探测失败时**跳过 PDF 并说明原因**，不会输出方框字。Linux 上可执行 `apt-get install fonts-wqy-zenhei`。

**中文断行**：xhtml2pdf 只会按**空格**断词，而中文没有空格，因此一整段中文会被画成单行冲出页面
右边界、超出部分被裁掉；它自带的 CJK 开关 `-pdf-word-wrap: CJK` 又存在 bytes/str 混用的实现缺陷，
一开启即抛 `TypeError`。因此 PDF 路径会先按标签字号估算每行可容纳的字数，主动插入 `<br/>`：

- 断点优先级为「中文标点后 → 汉字之间 → 空格后」，并保证标点不落到下一行行首
- **不会在英文单词中间断开**，期刊名与 URL 保持完整
- 仅对中文占比超过 50% 的段落生效，纯英文段落交给渲染器自行处理
- 只影响 PDF；Markdown 与 HTML 导出保持自然换行（浏览器本身就会折中文）

### 可观测性与成本核算

每次研究记录一棵 span 树（每个节点、每次 LLM 调用的耗时 / Token / 成本），
落盘到 `outputs/<时间戳>/trace.json`，并在 CLI 与前端展示。整次研究对应**一个 trace**，
节点是其子 span，LLM 调用是 generation span。由于 span 上下文同时就是 LangFuse observation，
上报的是**真实的起止时间**，而非事后重放的假耗时。

| 维度 | 处理方式 |
|---|---|
| 单价来源 | [DeepSeek 官方价目表](https://api-docs.deepseek.com/quick_start/pricing/)（美元/百万 tokens） |
| 高峰/错峰 | 高峰（UTC 周一至周五 01:00-04:00、06:00-10:00）为错峰价 2 倍，按当前时间自动判断 |

不影响研究本身。

### 2. 策略消融实验

```bash
python eval_research.py                  # 3 题 × 3 配置的完整矩阵
python eval_research.py --offline        # 离线自检，不消耗额度
python eval_research.py --no-judge       # 只跑客观指标，跳过 LLM 裁判
```

评估两套指标：**客观指标**（完成率、轮数、事实数、引用数、字数、Token、成本、耗时）来自内置插桩，
零额外成本；**报告质量**（忠实度、相关性、覆盖度、结构性，各 0~1）由自研 LLM 裁判打分，
每题一次调用。忠实度的判定方式是把报告正文与**它自己引用的事实清单**逐条比对，
裁判无需访问原始网页，也就无从编造验证。

三个消融配置：`full`（反思循环 + 本地知识库）、`no_reflect`（最大搜索轮数=1）、`no_local`（关闭本地库）。

#### 结果

| 配置 | 完成率 | 平均轮数 | 平均事实 | 平均引用 | 报告字数 | 裁判均分 | 平均 Token | 平均成本 | 平均耗时 |
|---|---|---|---|---|---|---|---|---|---|
| **full** | 100% | 3.0 | **118** | **17.3** | 8648 | 0.800 | 81,749 | ¥0.1370 | 261s |
| **no_reflect** | 100% | 1.0 | 35 | 5.3 | 5648 | 0.792 | 27,657 | ¥0.0520 | 70s |
| **no_local** | 100% | 3.0 | 119 | 19.3 | 10185 | 0.808 | 94,680 | ¥0.1560 | 330s |

#### 结论一：反思循环的收益显著

关闭补充搜索后，事实量从 118 降至 **35（−70%）**、引用从 17.3 降至 5.3、
覆盖率评分从 0.683 降至 0.567，而成本仅节省 62%。即**以 2.6 倍成本换取 3.4 倍证据量**。

#### 结论二：证据量与引用准确性存在权衡

| 配置 | 忠实度 | 覆盖度 |
|---|---|---|
| full | 0.750 | **0.683** |
| no_reflect | **0.883** | 0.567 |
| no_local | 0.750 | 0.717 |

事实量从 35 条增至 118 条时，忠实度由 0.883 降至 0.750，覆盖度则由 0.567 升至 0.683。
裁判给出的扣分点集中于**引用错配**，例如"F29 的 1.83 倍是 FP8 训练速度、
F30 的 12% 是 DualPipe 气泡率，报告将二者合并为同一因果表述"。
这表明"检索充分"与"引用准确"是两个独立问题，后者目前尚无专门优化。

#### 结论三：本地知识库在初始配置下为净负收益，并暴露两处实现缺陷

初始配置下，本地知识库引用仅占总引用的 **6%**（17.3 条中 1~2 条），
却占用了 40% 的阅读名额，使 T1 的网页阅读量由 29 篇降至 19 篇，事实数未见提升、成本反增 14%。

排查确认问题不在语料，而在两处实现：

1. **跨来源归一化尺度错误**：网页与本地库各自做 min-max 归一化，
   导致本地库哪怕只召回到弱相关片段，其中最强的一条也会被拉满至 1.0 并压过所有网页结果。
   修正为两路共用一个 min/max。
2. **40% 为硬配额**：低分本地片段同样占据名额。修正为保底 2 条 + 其余按融合分数自由竞争。

修正后同题（T1，full 配置）实测：

| | 修正前 | 修正后 |
|---|---|---|
| 抓取网页 | 19 篇 | **27 篇** |
| 读取本地片段 | 8 段 | 6 段（保底仍生效） |
| 提炼事实 | 106 条 | **141 条** |
| 引用来源 | 20 条 | **25 条** |

该结果说明：单次运行的报告"看起来完整"并不代表流程正确，需要靠横向对比才能定位此类缺陷。

## 🐳 Docker 部署

```bash
# 起 Web 界面
docker compose up -d --build
# 浏览器打开 http://localhost:8501

# 命令行跑一次研究
docker compose run --rm cli "2024 年以来国产大模型的推理成本下降了大约多少？"

# 环境体检 / 策略评估
docker compose run --rm doctor
docker compose run --rm eval
```

| 文件 | 作用 |
|---|---|
| `Dockerfile` | python:3.11-slim，换国内 Debian/pip 源，装中文字体，只装 CPU 版 torch |
| `docker-compose.yml` | web / cli / doctor / eval 四个服务；密钥走 `env_file`，数据与索引挂载到宿主机 |
| `.dockerignore` | `.env`、`.venv`、`outputs`、`chroma_db` 等一律不进镜像 |
| `.streamlit/config.toml` | headless 模式、端口 8501、关闭统计上报 |

设计要点：

- **密钥不进镜像**：`.env` 同时写入 `.dockerignore` 与 `.gitignore`，容器通过 `env_file` 读取
- **索引与模型缓存持久化**：`chroma_db` 挂载到宿主机，HuggingFace 模型放具名卷 `hf_cache`，
  重建容器无需重新下载模型或重建向量索引
- **装中文字体**（`fonts-wqy-zenhei`）：安装路径与 `report.py` 的 Linux 字体候选一致，
  否则容器内 PDF 导出会被自动跳过
- **只装 CPU 版 torch**：项目仅在 CPU 上运行 embedding，而 PyPI 上 Linux 的 torch 默认是 CUDA 版，
  会连带拉取约 2GB 的 `nvidia-*` 依赖。Dockerfile 先从国内镜像安装 `torch==2.6.0+cpu`，
  装 requirements 时 pip 即认为 torch 已满足
- **`cli` / `eval` 放在 profile 中**：`docker compose up` 不会顺带启动它们

> **镜像体积**：即便只装 CPU 版 torch，镜像仍有 3.17GB（torch 约 900MB + onnxruntime/pyarrow/scipy 等）。
> 若不需要本地知识库，可注释掉 `requirements.txt` 中的 `sentence-transformers` 与 `chromadb`，
> 并将 `.env` 的 `USE_LOCAL_KB` 设为 0，镜像可降至 1GB 以内。

### 国内网络环境部署说明

以下为实测结论，供网络受限环境参考：

**① 基础镜像拉取**：`registry-1.docker.io`、`auth.docker.io`、`hub.docker.com`、
`download.docker.com` 均不可达（连接被重置）。需配置镜像加速站——在 Docker Desktop 的
**Settings → Docker Engine** 中，或编辑 Linux 下的 `/etc/docker/daemon.json`，加入：

```json
{
  "registry-mirrors": ["https://docker.1panel.live"]
}
```

> `daemon.json` 是严格 JSON 格式，**不能包含注释**（写 `//` 会导致守护进程启动失败），
> 因此上述配置块中不含任何说明文字。

实测该加速站可正常拉取 `python:3.11-slim`（51 秒）。曾经常用的
`docker.mirrors.ustc.edu.cn`、`hub-mirror.c.163.com`、`dockerproxy.com` 目前均不可用。

**② CPU 版 torch 的镜像源差异**：同一个 wheel 实测
`mirror.sjtu.edu.cn` 为 **11.9 MB/s**，`mirrors.aliyun.com` 仅 **0.08 MB/s**（会导致构建超时）。
Dockerfile 默认使用前者，可通过 `--build-arg TORCH_WHEEL=...` 覆盖。
另需注意上交大的 `/cpu/` 是 PEP 503 包索引（按包名分子目录），不能作为 `--find-links` 扁平列表使用。

**③ Windows 家庭版的 Docker 安装**：Docker Desktop 官方安装包所在域名同样被重置，
国内镜像仅存旧版（`mirror.azure.cn` 实测 15.6 MB/s，版本停留在 Docker Desktop 4.1.1）。
家庭版必须依赖 WSL2，而 WSL2 官方下载源（`aka.ms`、`wslstorestorage`、GitHub Releases）亦不可达。
不依赖 Windows 管理员权限的可行路径：

```powershell
# 1) 管理员 PowerShell 中启用 WSL 功能（不下载发行版）
wsl --install --no-distribution
# 重启后：
# 2) 从清华镜像获取 rootfs 并导入（示例路径可自行调整）
curl.exe -L -o "$env:USERPROFILE\Downloads\ubuntu-base-24.04.tar.gz" `
  "https://mirrors.tuna.tsinghua.edu.cn/ubuntu-cdimage/ubuntu-base/releases/24.04/release/ubuntu-base-24.04.3-base-amd64.tar.gz"
wsl --import DeepResearch D:\WSL\DeepResearch "$env:USERPROFILE\Downloads\ubuntu-base-24.04.tar.gz" --version 2
```

进入发行版后换用国内 apt 源，执行 `apt-get install -y docker.io docker-compose-v2`，
并配置 `/etc/wsl.conf` 的 `[boot] command` 以随 WSL 自动启动 dockerd。

## 🐛 踩坑与解决

以下为开发过程中遇到并已修复的问题，按「现象 / 原因 / 解决」记录。
其中第 1~3 条是**实际使用中暴露**的严重缺陷，也是 `tests/test_bugfix.py` 的由来。

### 1. 离线假模型泄漏到真实运行（真搜索 + 假模型）

**现象**：切换到「真实运行」后，研究计划变成"背景是什么？""现状如何？""风险在哪？"，
报告正文是"离线自检章节正文。此处用于验证写作节点的解析逻辑"，但**参考文献却是真实网址**。
即搜索是真的、模型是假的，两者拼在一起，报告与问题完全不相干。

**原因**：`DeepResearchAgent.__init__(llm=...)` 早期通过 `llm.set_llm(llm)` 注入假模型，
而 `set_llm` 改写的是**进程级全局单例**。Streamlit 进程常驻，用户先跑一次「离线演示」后，
全局默认模型被替换为假模型；切回「真实运行」时 `DeepResearchAgent(llm=None)` 不会重置它，
于是继续使用假模型。而搜索函数是在上下文管理器里临时替换的，退出即恢复，因此只有搜索是真的。

**解决**：引入**作用域级**的 `use_llm()`（基于 `contextvars`），只对本次 `plan()` / `run()` 生效，
退出自动恢复；`DeepResearchAgent` 不再触碰全局；`set_llm()` 降级为仅供测试夹具并加注释警示；
新增 `reset_llm()`，前端在真实模式入口再调用一次作为二次防护。

### 2. 把 PDF 二进制当网页正文，导致满屏乱码

**现象**：网页与导出的 PDF 中出现大量乱码，字符替换符（U+FFFD）占比高达 42%~58%。

**原因**：Trafilatura 对 PDF 抽不出正文时回退到 `requests + BeautifulSoup`，
而 requests 会把 PDF 字节按文本解码，得到上万字符的乱码"正文"，又恰好通过了
`len(text) >= 200` 的长度检查，于是被当作正常网页送进提炼环节。

**解决**：加五道防线——① 检查 `Content-Type`（`application/pdf`、`image/*`、`zip` 等一律拒绝）；
② 检查文件头是否为 `%PDF`；③ URL 以 `.pdf/.docx/.zip` 结尾的直接跳过，不发请求；
④ 新增 `looks_like_binary()`，异常字符占比超过 1% 即判定为二进制并丢弃；
⑤ `_clean_text()` 剔除替换字符与控制字符。修复后实测最高乱码占比为 0.000%。

### 3. 子问题缺少主语，导致检索结果与问题完全不相干

**现象**：拆解出的子问题是"背景是什么？""现状如何？""风险在哪？"，脱离原研究问题后无法理解。

**原因**：两层。表层是第 1 条缺陷造成的（那是假模型写死的台词）；深层是
`PLANNER_PROMPT` 里写着"先摸清背景与现状，再深入机制/数据/对比"——
这等于在教模型把子问题写成"背景是什么？"。而子问题没有主语时，检索词会退化成
"背景""现状"这类泛词，搜回的内容自然与真问题无关，进而污染整份报告。

**解决**：① Prompt 中直接给出反例与正例，明确要求"每个子问题都必须是完整问句且带上研究主体"；
② 规则层加 `is_self_contained()` 检出无主语小标题，用一次补救 Prompt 改写，
仍不合格则程序化拼接研究主体；③ 检索词的泛词检查；④ 判定刻意保守（只拦长度不足或整句为泛化名词的），
避免误杀"MoE 架构对推理成本的影响？"这类引入新概念但完全正当的子问题。

### 4. xhtml2pdf 不会给中文折行，段落冲出页面被裁掉

**现象**：PDF 文字左侧页边距异常大、右侧几乎为零，大段文字缺失。

**原因**：xhtml2pdf 只按**空格**断词，中文没有空格，因此整段中文被当成一个超长单词，
直接画到页面外并被裁掉（实测 108 字的中文段落被画成单行；同样长度的英文段落能正常折行）。
它自带的 CJK 开关 `-pdf-word-wrap: CJK` 又存在 bytes/str 混用的实现缺陷，
一开启即抛 `TypeError: sequence item 0: expected a bytes-like object, str found`。
插入零宽空格（U+200B）同样无效——中文字体没有该字形，反而渲染成空白框。

**解决**：PDF 渲染前按标签字号估算每行可容纳的字数，主动插入 `<br/>`：
断点优先级为「中文标点后 → 汉字之间 → 空格后」，保证标点不落到行首、
不在英文单词中间断开，仅对中文占比超过 50% 的段落生效。修复后最长行由 343 字符降为
约 49 个全角单位（上限 47），页数由 4 页增至 6 页——原先被裁掉的内容全部显示出来。

### 5. xhtml2pdf 静默降级导致 PDF 中文变成方框

**现象**：PDF 能正常生成，但中文全部渲染为方框或空白，且**不报任何错误**，
仅在日志中留下一句 `None of the font families 'reportcjk' is known to this document`。

**原因**：xhtml2pdf 0.2.20 起引入资源沙箱（`ResourceAccessPolicy`），
文档只能读取自身所在目录，因此 `C:\Windows\Fonts` 下的字体被判为越权读取。
另经对照实验确认，HTML 的 `<title>` 标签因不在 `<body>` 内也不会继承正文字体。

**解决**：① 按最小授权原则，仅将字体所在目录加入沙箱白名单，保留默认 SSRF 防护；
② 通过 `@font-face` 内嵌字体，并用 `*` 全局选择器覆盖 `<title>` 等元素；
③ 捕获 xhtml2pdf 日志，并用 pypdf 把 PDF 文字抽回核对中文，
把"静默降级"变为"明确失败"。PDF 大小由 2.8KB（Helvetica 空壳）变为 71.8KB（字体已内嵌）。

### 6. 跨来源分别归一化导致本地库压过网页结果

**现象**：开启本地知识库后，本地引用仅占总引用 6%，却占用了 40% 的阅读名额。

**原因**：网页与本地库**各自**做 min-max 归一化。各自拉伸后，本地库哪怕只召回到
一堆弱相关片段，其中最强的一条也会被拉满至 1.0（再乘 1.15 加权），必然压过所有网页结果。

**解决**：改为两路共用同一个 min/max 归一化，保留跨来源的相对强弱。
修正后同一道题的网页阅读量由 19 篇升至 27 篇，事实数由 106 条升至 141 条。

### 7. 冲突检测把 URL 中的编号当作数据矛盾

**现象**：一次运行报告 25 组"互相矛盾的数据"，但实际数据中并不存在矛盾。

**原因**：初版判定条件为"文本相似度 ≥ 0.55 且数字不同"，而事实中携带来源 URL
（如 `.../page-3`），正则把 URL 中的编号也当成了数据。

**解决**：改为严格判定——去除 URL 后把数字替换为占位符，**两句话必须完全一致**、
仅数字不同才算矛盾。修正后误报由 25 组降为 0，真实矛盾仍可识别。

### 8. 检索词判重阈值过低导致有效检索词被丢弃

**现象**：反思环节给出 2 个补充检索词，日志只显示"补充 1 个"。

**原因**：`SequenceMatcher` 相似度阈值设为 0.75，而"离线自检 补充证据1"与
"离线自检 数据1"的相似度恰好为 0.750，第二个词被判为重复而丢弃。
中文检索词常有共同前缀，该阈值对短中文串区分度不足。

**解决**：阈值提高到 0.90；包含关系判定增加长度保护（短词须不短于长词的 60%，
否则"AI"会命中一切检索词）。

### 9. Chroma 的 relevance score 越界，阈值无法标定

**现象**：控制台出现 `UserWarning: Relevance scores must be between 0 and 1`，
实测出现 `-0.02` 这类负分，相关度闸门失效。

**原因**：`similarity_search_with_relevance_scores` 的取值范围取决于 collection 的距离度量，
BGE 归一化向量配 L2 空间时会越界。

**解决**：显式声明 `hnsw:space=cosine`，改用 `1 - distance` 自行计算相似度并裁剪至 [0,1]，
随后重新标定阈值为 0.45。

### 10. Chroma 客户端并发竞态

**现象**：真实运行中出现 `searcher 3 个检索任务失败`。

**原因**：5 个子问题并发查询本地库，而 Chroma 的持久化客户端不允许同一进程对同一目录
重复实例化，索引重建更不能并发执行。

**解决**：`local_kb` 中加入可重入锁，保证全进程单实例。并新增并发回归测试
（8 线程并发首次检索 + 清缓存后并发重建）。

### 11. 并发子线程无法继承追踪上下文

**现象**：`inherit_context(fn)` 交给 `pool.map` 复用时抛出
`RuntimeError: cannot enter context: <Context> is already entered`。

**原因**：`pool.map` 只会求值一次包装函数，多个任务共用同一个 `contextvars.Context`，
而 Context 不允许被并发进入。

**解决**：包装时抓取快照，**每次执行时再复制一份新副本**。这样无论调用方是
"每次提交都包装一次"还是"包装一次后复用"，均不会出错。
该问题通过真实 OpenTelemetry 内存导出器验证（含不继承上下文的反证）。

### 12. 缺少根 span 导致一次研究裂成多条 trace

**现象**：自检断言"节点 span 都是根 span 的子节点"失败——5 个节点 span 的 parent 均为空。

**原因**：只为节点添加了 span，未为"整次研究"添加根 span。LangFuse v4 基于 OpenTelemetry，
顶层 observation 会各自开启新 trace，界面上表现为 5 条互不相干的记录。

**解决**：在 `graph.invoke` 外层包裹 `research` 根 span。修正后 trace 树为
1 个根 + 所有节点作为其直接子节点。

### 13. 报告附录统计显示为 0

**现象**：同一份报告中，指标表显示"Token 消耗 108244"，正文附录却写着"LLM 调用：0 次，Token 0"。

**原因**：`render_report_markdown` 在 `writer` 节点内执行，而耗时与 Token 需等整张图跑完才有值。

**解决**：在 `run()` 中待 stats 定稿后重新渲染报告，并同步更新报告字数。
